# LLM Usage SwiftBar 多平台需求说明

## 1. 文档目的

本文件用于维护插件的产品需求与边界。  
README 仅用于安装与使用说明，不承载需求讨论。

## 2. 项目目标

将当前插件演进为通用的 SwiftBar 菜单栏用量插件，支持多平台接入与统一展示，便于后续贡献者快速扩展新平台。

## 3. 平台范围与优先级

### 3.1 当前目标平台

1. `new_api` 类第三方 token 供应商（优先）
2. `Cursor`
3. `Trae.ai`

### 3.2 接入策略

- 优先接官方或稳定接口。
- 非官方接口优先级低。
- 本地日志解析优先级低。
- 无法自动拉取时，允许手工配置窗口作为兜底。

## 4. 架构要求

### 4.1 总体原则

- 先统一架构，再逐个平台接入。
- Provider 适配层与渲染层解耦。
- 新平台应以最小改动接入，不影响已有平台。

### 4.2 展示层级

统一展示结构必须为：**平台 > 账号 > 窗口**。

### 4.3 主账号规则

- 支持指定主账号。
- 菜单栏顶部主指标取自主账号。

## 5. 用量窗口模型

统一支持六类窗口：

1. 日
2. 5小时
3. 周
4. 月
5. 自定义
6. 不重置

说明：

- 允许不同平台返回不同单位与字段。
- 以平台可得数据为准，不强行统一单位。

## 6. 配置与交互要求

### 6.1 配置入口

- 所有平台接入配置应通过 SwiftBar 图形交互完成。
- 不要求用户直接编辑配置文件。

### 6.2 账号能力

- 支持多账号并存（同平台可多个账号）。
- 支持账号级增删改与主账号切换。

### 6.3 手工窗口能力

- 支持手工新增、清空窗口。
- 作为官方接口不可用时的标准降级路径。

## 7. 安全与存储

- 允许使用 macOS Keychain 存储密钥信息。
- 允许将非敏感信息（如 Base URL）存于本地配置文件。

## 8. `new_api` 兼容要求

- 第三方供应商范围难以完整定义，应采用“问题驱动、逐步兼容”策略。
- 先提供通用接入版式，再按实际供应商问题扩展字段解析与接口探测。
- `new_api` 新增账号时，必须采用**单弹窗配置**（同一弹窗完成 `api` 与 `api_token` 输入）。

### 8.1 `new_api` 单弹窗交互

- 该约束仅适用于 `new_api`，不要求 Cursor/Trae 复用。
- 单弹窗必须提供：
  - `api` 输入（支持 Base URL 或完整 Usage Endpoint）
  - `api_token` 输入
  - `测试连接` 按钮
  - `保存配置` 按钮
- `测试连接` 行为：只测试，不保存。

### 8.2 三级校验（红绿灯）

测试连接必须输出三级结果，并分别以 🟢/🔴 标识：

1. **一级：API 可达性**
   - 标准：HTTP 可达（可收到 HTTP 状态码即视为可达）。
2. **二级：Token 可用性**
   - 需要明确用于验证 token 的完整 endpoint。
   - 系统必须给出可解释结论（通过/失败及对应 URL/状态）。
3. **三级：用量可用性**
   - 必须解析出以下之一（字段名可异构）：
     - `used/total/remaining` 组合
     - `utilization`（或等价字段）

### 8.3 Base URL / 完整 Endpoint 判定

- 用户输入 **Base URL** 时：
  - 第三级应按候选后缀逐一探测。
- 用户输入 **完整 Usage Endpoint** 时：
  - 第三级只对该 endpoint 校验一次。

### 8.4 保存门禁

- 测试失败不允许保存。
- 仅当三级全部绿色时，才允许保存配置。

## 9. 非目标（当前阶段）

- 不优先实现基于非官方接口的稳定自动采集。
- 不优先实现本地日志解析链路。
- 不要求恢复或优先维护旧的 Claude Code 专用路径。

## 10. 迭代原则

- 以“可扩展性”和“贡献者易接入”为第一优先。
- 每次新增平台或能力时，先补充本 spec，再实现代码与 README 使用说明。
